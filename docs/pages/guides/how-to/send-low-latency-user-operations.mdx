# How to send user operations with the lowest latency

This guide shows you how to land a user operation as fast as Pimlico can: it goes into its own bundle right away and its receipt comes back in the same call, with no mempool wait or receipt polling. Use it when your app needs the result before it can continue, such as a payment or a trade.

## How fast it is

Median time from signing until the receipt is in hand, against Pimlico's production bundler:

| Chain | `sendUserOperation` + poll | `sendUserOperationSync` | Faster by |
| :--- | ---: | ---: | ---: |
| Base | 697 ms | **364 ms** | 333 ms (48%) |
| BSC | 728 ms | **294 ms** | 434 ms (60%) |
| Robinhood | 258 ms | **182 ms** | 76 ms (29%) |

It is almost as fast as sending the same call from an EOA:

| Chain | `sendUserOperationSync` | EOA send + poll |
| :--- | ---: | ---: |
| Base | **364 ms** | 255 ms |
| BSC | **294 ms** | 340 ms |
| Robinhood | **182 ms** | 100 ms |

The EOA sends with `eth_sendRawTransaction`, then polls `eth_getTransactionReceipt`.

For how these were measured, see the [`sendUserOperationSync` reference](/references/permissionless/reference/pimlico-actions/sendUserOperationSync).

## If the send throws

`sendUserOperationSync` never resends on its own. When it throws a `SendUserOperationSyncError`, decide from its `kind`:

- If `kind` is `pending`, the user operation may have been sent. Wait for its receipt and don't resend.
- If `kind` is `bundle_reverted`, another bundler may have included the user operation first. Check for its receipt, and resend only if there is none.
- If `kind` is `not_found`, nothing was sent. Send the same calls again.
- If `kind` is `rejected`, the bundler rejected the user operation before sending it. Fix the cause in `error.cause`, then send again.

## Send several user operations from one account

Await each `sendUserOperationSync` call before sending the next one. A user operation sent while the previous one from the same account is still in flight is rejected with `AA25 invalid account nonce`.

- On Base, if the next user operation is rejected with `AA25` right after the previous receipt, resend it after 1–2s.
- To send in parallel from one account, give each user operation its own nonce key. See [How to send user operations in parallel](/guides/how-to/parallel-transactions).
