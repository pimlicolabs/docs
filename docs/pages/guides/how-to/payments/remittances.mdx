# Gasless stablecoin remittances

A remittance app can let users send USDC across borders without ever holding ETH by giving each user an ERC-4337 smart account and attaching a paymaster to every transfer. With Pimlico, either your app pays the network fee through the **verifying paymaster**, capped by a **sponsorship policy** (global, per-user and per-user-operation spending limits, operation counts, and a chain allowlist), or the user pays it in USDC through the **ERC-20 Paymaster**, which takes the fee from the sender in the same user operation. Users who already have an EOA can keep their address by upgrading it with EIP-7702.

Pimlico covers gas and transaction inclusion. Converting fiat to and from stablecoins, and moving funds between chains, are outside its scope and need an on/off-ramp or bridge provider.

## How the pieces fit

- **Smart account**: each user's USDC sits in an ERC-4337 account (here a Simple account) controlled by their signer: an embedded wallet, a passkey, or their own key.
- **Bundler**: Pimlico's bundler takes the signed user operation and gets it on chain, paying the ETH for the transaction up front.
- **Verifying paymaster + sponsorship policy**: Pimlico covers the user operation's gas and charges your off-chain Pimlico balance. The policy decides how much you're willing to spend.
- **ERC-20 Paymaster (fallback)**: when you don't sponsor a transfer, the paymaster covers the gas and takes the equivalent in USDC from the sender's account.

This guide uses Base and its native USDC (`0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`). The same code works on any [supported chain](/guides/supported-chains): change the chain, the RPC URL and the USDC address, and check the [ERC-20 Paymaster's supported tokens](/references/paymaster/erc20-paymaster/supported-tokens) if you use the fallback.

## Steps

::::steps

### Create a sponsorship policy

A sponsorship policy is a set of hosted rules that Pimlico checks before it signs a sponsorship. For remittances, the useful controls are:

- a **global** spending limit (for example per month) so a traffic spike can't drain your balance,
- a **per-user** limit on spend or on the number of user operations (for example a few free transfers per day),
- a **per-user-operation** spending cap,
- a **chain allowlist**, so the policy only sponsors on the chains you operate on,
- optional **start and end times**.

You can create the policy in the [dashboard](https://dashboard.pimlico.io/sponsorship-policies), with the [Pimlico CLI](/references/platform/cli), or with the [Sponsorship Policies API](/references/platform/api/sponsorship-policies/create). Amounts are in US cents, so `50` is $0.50. The values below are examples; pick limits that match your unit economics.

```bash
curl -X POST "https://api.pimlico.io/v2/account/sponsorship_policies?apikey=YOUR_PIMLICO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "policy_name": "Remittances on Base",
    "chain_ids": { "allowlist": [8453] },
    "limits": {
      "global": {
        "user_operation_spending": { "amount": 500000, "currency": "USD" },
        "reset_interval": "monthly"
      },
      "user": {
        "maximum_user_operation_count": 5,
        "reset_interval": "daily"
      },
      "user_operation": {
        "user_operation_spending": { "amount": 50, "currency": "USD" }
      }
    }
  }'
```

The response contains the policy `id` (for example `sp_mighty_chameleon`). You'll pass it as `sponsorshipPolicyId` when you request sponsorship. See [the Sponsorship Policy object](/references/platform/api/sponsorship-policies/object) for every field.

### Only sponsor USDC transfers (optional)

Spending limits don't restrict *what* a user operation does. If you only want to pay for USDC transfers made by your own customers, enable a [sponsorship policy webhook](/guides/how-to/sponsorship-policies/webhook). Pimlico sends the user operation to your endpoint and only sponsors it if you answer `{ "sponsor": true }`.

The handler below verifies the webhook signature with `@pimlico/webhook`, decodes the account's call data with its `parseCallData` helper, and approves the request only if every contract call is a USDC `transfer` from an account you recognize.

```ts [app/api/pimlico-webhook/route.ts]
import { parseCallData, pimlicoWebhookVerifier } from "@pimlico/webhook"
import { type Address, isAddressEqual, slice, toFunctionSelector } from "viem"

const USDC = "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913" // USDC on Base
const TRANSFER_SELECTOR = toFunctionSelector("transfer(address,uint256)")

const verifyWebhook = pimlicoWebhookVerifier(process.env.PIMLICO_WEBHOOK_SECRET as string)

// Your own lookup, e.g. "is this smart account a KYC'd user of my app?"
declare function isActiveCustomer(sender: Address): Promise<boolean>

export async function POST(request: Request): Promise<Response> {
	const body = await request.text()

	let event: ReturnType<typeof verifyWebhook>
	try {
		event = verifyWebhook(Object.fromEntries(request.headers), body)
	} catch {
		return new Response("invalid signature", { status: 401 })
	}

	if (event.type !== "user_operation.sponsorship.requested") {
		// e.g. "user_operation.sponsorship.finalized": record it and acknowledge
		return Response.json({ received: true })
	}

	const { userOperation } = event.data.object

	// parseCallData decodes the account's execute / executeBatch call data
	const contractCalls = parseCallData(userOperation.callData).filter(
		(call) => call.data !== "0x",
	)

	const onlyUsdcTransfers =
		contractCalls.length > 0 &&
		contractCalls.every(
			(call) =>
				isAddressEqual(call.to, USDC) &&
				slice(call.data, 0, 4).toLowerCase() === TRANSFER_SELECTOR,
		)

	const sponsor = onlyUsdcTransfers && (await isActiveCustomer(userOperation.sender))

	return Response.json({ sponsor })
}
```

:::note
`parseCallData` flattens nested calls and also returns a decoded `transfer` as an extra entry with `data: "0x"`, which is why the filter only inspects entries that carry call data. Simple and EIP-7702 Simple accounts batch with `executeBatch`; Safe batches go through a MultiSend contract, so adjust the rule if you use Safe.
:::

## Running this in production

- **Funding sponsorship**: the verifying paymaster charges your off-chain Pimlico balance or attached card. When you request sponsorship, Pimlico holds the user operation's maximum possible cost and refunds the difference after it lands. See the [verifying paymaster FAQ](/references/paymaster/verifying-paymaster/faqs).
- **Sponsorship validity**: a sponsorship signature is valid for 10 minutes by default. If users may sign and submit later, extend it with `validForSeconds` ([guide](/guides/how-to/paymasters/extending-sponsorship-duration)). ERC-20 Paymaster sponsorships are always valid for 10 minutes.
- **Several chains**: the API, the clients and the code are the same on every chain Pimlico supports. Create one policy per chain, or one policy whose `chain_ids.allowlist` lists all of them.
