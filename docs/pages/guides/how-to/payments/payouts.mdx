# How to send USDC payouts to thousands of recipients

This guide shows you how to pay thousands of recipients in USDC from a **smart account treasury**, by batching `transfer` calls into ERC-4337 user operations and sending them **in parallel**, with gas sponsored by the **verifying paymaster** or paid from the treasury's USDC by the **ERC-20 Paymaster**. Batching removes the per-transaction overhead, but every transfer still costs its own execution gas, so measure what a chunk costs on your chain instead of assuming a price.

### Create the treasury client

This example uses a Safe as the treasury on Base, with EntryPoint 0.7. Keep the treasury key in a signer service such as [Turnkey](/guides/how-to/signers/turnkey), [Fireblocks](/guides/how-to/signers/fireblocks) or [Dfns](/guides/how-to/signers/dfns), not in an environment variable. For a treasury that needs several approvers, see [Safe with multiple signers](/guides/how-to/accounts/use-safe-account-with-multiple-signers).

By default the verifying paymaster sponsors the gas from your Pimlico balance. To pay it from the treasury's USDC through the ERC-20 Paymaster instead, set `paymasterContext: { token: USDC }` on the client; the `prepareUserOperationForErc20Paymaster` override only acts in that case.

If you sponsor, keep your Pimlico balance above the maximum cost of all chunks in flight: Pimlico holds each sponsored user operation's maximum possible cost until it lands, then refunds the difference ([FAQ](/references/paymaster/verifying-paymaster/faqs)).

### Deploy the treasury before sending in parallel

Send one user operation from the treasury on its own and wait for its receipt before you send any chunks. Parallel user operations only work once the account is deployed: if several of them carry the account's `factory` data, they conflict and fail with AA10. The send code below checks `treasury.isDeployed()` and stops if it isn't.

Transfers to addresses that have never held USDC usually cost more gas than transfers to existing holders, because a new storage slot is written. Measure with a realistic mix of recipients, then pick a chunk size that leaves plenty of headroom: a user operation runs inside a single bundle transaction, so it must fit within what the chain allows for one transaction and what the bundler accepts.

### Give every chunk a deterministic nonce

Derive the nonce key from the payout run ID and the chunk index. User operations with different keys run in parallel, and each `(key, sequence)` pair can be used only once ([nonce keys](/guides/how-to/parallel-transactions)), so a retried chunk reuses its nonce and can't pay twice. If the original is still in the bundler's mempool, the retry replaces it only if it raises both gas fees by at least 10%; otherwise it's rejected. Either way, only one of them can execute.

## Estimate the cost of a payout run

There's no fixed price per recipient. Work it out from your own measurements:

- **Before sending**: `getRequiredPrefund` on a prepared chunk is the upper bound in wei. In ERC-20 mode, `pimlicoClient.estimateErc20PaymasterCost({ userOperation, token })` returns the same bound in USDC and in USD (6 decimals), see [calculate costs](/guides/how-to/erc20-paymaster/how-to/calculate-costs).
- **After sending**: `receipt.actualGasCost` is what the chunk actually cost in wei. Sum it across chunks for the run's gas spend.
- **Billing**: sponsored gas is charged to your Pimlico balance ([verifying paymaster FAQ](/references/paymaster/verifying-paymaster/faqs)); in ERC-20 mode it is paid from the treasury's USDC.

For predictable, high-volume sponsored workloads, [Boosted Sponsorships](/guides/boosted-paymaster/use-boosted-paymaster) (available on request) skip the paymaster round trips and settle the gas off-chain on your monthly invoice.
