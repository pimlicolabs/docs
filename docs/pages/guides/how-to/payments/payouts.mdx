# Stablecoin payouts at scale

A payout platform can send USDC to thousands of recipients by holding funds in a **smart account treasury** and packing many `transfer` calls into each ERC-4337 user operation, so one signature and one round of validation cover a whole chunk of recipients. Chunks are sent **in parallel** by giving each user operation its own nonce key, and gas is either sponsored from your Pimlico balance by the **verifying paymaster** or paid from the treasury's USDC by the **ERC-20 Paymaster**. Batching removes the per-transaction overhead you'd pay with one transaction per recipient, but every ERC-20 transfer still costs its own execution gas, so measure what a chunk costs on your chain instead of assuming a price.

## Limits to design around

- **Gas per user operation.** A user operation runs inside a single bundle transaction, so its gas limits must fit within what the chain allows for one transaction and what the bundler will accept. Keep chunks well below that and size them by measurement (step 3).
- **All or nothing per chunk.** If one transfer in a batch reverts (for example a USDC-blacklisted recipient, or an insufficient balance), the whole user operation reverts and none of that chunk's transfers happen. Validate recipients before you build chunks.
- **Parallelism.** Pimlico's bundler currently supports up to 100 parallel user operations; contact support if you need more ([parallel transactions](/guides/how-to/parallel-transactions)). Use a concurrency limit well below that.
- **Deploy first.** Parallel user operations only work once the treasury account is deployed. If several of them carry the account's `factory` data, they conflict and fail with AA10.
- **Sponsorship holds.** When you sponsor, Pimlico holds each user operation's maximum possible cost from your balance until it lands, then refunds the difference ([FAQ](/references/paymaster/verifying-paymaster/faqs)). Many large chunks in flight need a balance that covers all of their maximums at once.

Transfers to addresses that have never held USDC usually cost more gas than transfers to existing holders, because a new storage slot is written. Measure with a realistic mix of recipients, then pick a chunk size that leaves plenty of headroom.

### Give every chunk a deterministic nonce

A smart account nonce has two parts: a 192-bit **key** and a 64-bit **sequence**. User operations with different keys are independent, which is what lets them run in parallel. Each `(key, sequence)` pair can be used only once.

Derive the key from the payout run and the chunk index. If your job crashes and retries a chunk, the retry uses the same nonce, so the chunk is paid at most once. If the original already landed, the retry fails validation with an invalid nonce instead of paying again. If the original is still in the bundler's mempool, the retry is rejected with AA25 unless it raises both gas fees by at least 10%, in which case it replaces the original. Either way, only one of them can execute.

## Estimating the cost of a payout run

There's no fixed price per recipient. Work it out from your own measurements:

- **Before sending**: `getRequiredPrefund` on a prepared chunk is the upper bound in wei. In ERC-20 mode, `pimlicoClient.estimateErc20PaymasterCost({ userOperation, token })` returns the same bound in USDC and in USD (6 decimals), see [calculate costs](/guides/how-to/erc20-paymaster/how-to/calculate-costs).
- **After sending**: `receipt.actualGasCost` is what the chunk actually cost in wei. Sum it across chunks for the run's gas spend.
- **Billing**: sponsored gas is charged to your Pimlico balance ([verifying paymaster FAQ](/references/paymaster/verifying-paymaster/faqs)); in ERC-20 mode it is paid from the treasury's USDC.

For predictable, high-volume sponsored workloads, the [Boosted Paymaster](/guides/boosted-paymaster/use-boosted-paymaster) (available on request) skips the paymaster round trips and bills the gas off-chain.
