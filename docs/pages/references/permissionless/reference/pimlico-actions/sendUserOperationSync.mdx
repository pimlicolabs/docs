# sendUserOperationSync

**This is the coolest thing we've shipped: the fastest way to land a smart account transaction on Pimlico.**

`sendUserOperationSync` sends a user operation straight into its own bundle and returns the receipt in the same call. There is no mempool wait and no receipt polling.

Against Pimlico's production bundler, it lands a user operation up to **60% faster** than `sendUserOperation` with receipt polling:

| Chain | `sendUserOperation` + poll | `sendUserOperationSync` | Faster by |
| :--- | ---: | ---: | ---: |
| Base | 697 ms | **364 ms** | 333 ms (48%) |
| BSC | 728 ms | **294 ms** | 434 ms (60%) |
| Robinhood | 258 ms | **182 ms** | 76 ms (29%) |

It is almost as fast as sending the same call from an EOA:

| Chain | `sendUserOperationSync` | EOA send + poll |
| :--- | ---: | ---: |
| Base | **364 ms** | 255 ms |
| BSC | **294 ms** | 340 ms |
| Robinhood | **182 ms** | 100 ms |

The EOA sends with `eth_sendRawTransaction`, then polls `eth_getTransactionReceipt`.

<details>
<summary>How we measured</summary>

- Median (p50) over 20 rounds per chain (40 on Robinhood), in October 2026. The cases run in a shuffled order every round.
- Each case lands the same 0-value call on mainnet. User operations are [boosted](/guides/boosted-paymaster/use-boosted-paymaster) and sent to `api.pimlico.io`.
- Each sample is timed from signing until the client holds the receipt. Gas limits, fees and nonces are prepared before the timer starts.
- The client runs in New York, the same region as Pimlico's bundler. The EOA transactions go through a commercial RPC provider's node in New York.
- `sendUserOperation` + poll calls `eth_getUserOperationReceipt` every 100 ms. EOA send + poll calls `eth_getTransactionReceipt` every 100 ms.
- All three cases ran together in a single run per chain.

</details>

`sendUserOperationSync` prepares and signs the user operation the same way as [`sendUserOperation`](/references/permissionless/reference/smart-account-actions/sendUserOperation), then sends it with [`pimlico_sendUserOperationNow`](/references/bundler/endpoints/pimlico_sendUserOperationNow).

Available on Base, BSC and Robinhood, with EntryPoint 0.7 and 0.8.

## Returns

- **Type:** `UserOperationReceipt`

The receipt of the included user operation, the same object [`waitForUserOperationReceipt`](/references/permissionless/reference/smart-account-actions/waitForUserOperationReceipt) returns.

- Check `success`: it is `false` if the call reverted inside the account, in which case the nonce is used.
- On Base, the receipt arrives before its block is sealed, so `receipt.blockHash` can be all zeros. Use `receipt.blockNumber` and `receipt.transactionHash` instead.
- The bundler doesn't queue user operations, so send them from one account one after another, or use different nonce keys. See [Nonces](/references/bundler/endpoints/pimlico_sendUserOperationNow#nonces).

## Parameters

`sendUserOperationSync` takes the same parameters as viem's [`sendUserOperation`](https://viem.sh/account-abstraction/actions/bundler/sendUserOperation), such as `calls`, `account` and the gas fields, plus the following.

### timeout (optional)

- **Type:** `number`
- **Default:** `client.transport.timeout`, else `10_000`

Time (ms) from sending the user operation to having its receipt. It covers the bundler call and any receipt polling, and every request is raced against it.

### pollingInterval (optional)

- **Type:** `number`
- **Default:** `client.pollingInterval`

How often (ms) to poll for the receipt.

## Errors

`sendUserOperationSync` never resends a user operation on its own. When it can't return a receipt, it throws a `SendUserOperationSyncError` with:

- `kind`: what happened.
- `canResend`: whether sending the same user operation again is safe.
- `userOperationHash`: the hash to track the user operation with.

| `kind` | What happened | `canResend` |
| :--- | :--- | :--- |
| `rejected` | The bundler rejected the user operation before sending it, for example for an invalid nonce or a failed simulation. Nothing was sent. `cause` holds the viem user operation error. On Base, an `AA25 invalid account nonce` right after the previous receipt clears if you resend after 1–2s. | `false` |
| `bundle_reverted` | The bundle landed but reverted, so it didn't execute the user operation. The message is the bundler's. Another bundler may have included the user operation first, so check `getUserOperationReceipt` before resending. | `true` |
| `pending` | The user operation may have been sent, but there was no receipt before `timeout`: the bundler said it was sent but not included yet, or didn't answer in time. Keep polling for its receipt instead of resending. | `false` |
| `not_found` | The bundler couldn't send the bundle (`-32603`), and no receipt showed up before `timeout`. | `true` |

```ts
import { SendUserOperationSyncError } from "permissionless/actions/pimlico"

try {
    const receipt = await smartAccountClient.sendUserOperationSync({ calls })
} catch (error) {
    if (!(error instanceof SendUserOperationSyncError)) throw error

    if (error.kind === "pending") {
        // May have been sent: wait for it, don't resend
        await smartAccountClient.waitForUserOperationReceipt({
            hash: error.userOperationHash
        })
    } else if (error.kind === "bundle_reverted") {
        // Another bundler may have included it first: check before resending
    } else if (error.canResend) {
        // not_found: safe to send the same user operation again
    }
}
```
