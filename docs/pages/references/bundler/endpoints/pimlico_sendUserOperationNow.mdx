# pimlico_sendUserOperationNow

`pimlico_sendUserOperationNow` is a Pimlico bundler method that bundles one signed user operation in its own bundle right away and returns its receipt in the same response.

Sends a signed user operation in its own bundle right away and returns its receipt in the same response. There is no mempool wait and no receipt polling. From TypeScript, use [`sendUserOperationSync`](/references/permissionless/reference/pimlico-actions/sendUserOperationSync), which also handles the errors below. Its page has the latency benchmarks.

Available on Base, BSC and Robinhood, with EntryPoint 0.7 and 0.8.

:::info[Contact us to enable it]
`pimlico_sendUserOperationNow` is enabled on request. [Contact us](https://cal.com/team/pimlico/20min) or email [support@pimlico.io](mailto:support@pimlico.io) to turn it on for your API key and chains.
:::

## Usage

The parameters are the same as [`eth_sendUserOperation`](/references/bundler/endpoints/eth_sendUserOperation): the user operation and the EntryPoint address.

A [boosted user operation](/guides/boosted-paymaster/use-boosted-paymaster) on Base with EntryPoint 0.8: `maxFeePerGas` and `maxPriorityFeePerGas` are `0` and every paymaster field is empty. The gas is billed to your Pimlico balance.

## Returns

- **Type:** `RpcUserOperationReceipt`

The user operation receipt, once the user operation is included: the same object [`eth_getUserOperationReceipt`](/references/bundler/endpoints/eth_getUserOperationReceipt) returns. Numbers are hex.

`success: false` means the user operation was included but its call reverted inside the account. Its nonce is used.

On Base, the receipt arrives before its block is sealed, so `receipt.blockHash` can be all zeros. Use `blockNumber` and `transactionHash` instead.

## Errors

Errors are standard JSON-RPC errors. `error.data` is only set when a bundle was sent, and holds `userOpHash` and `transactionHash`. **If `data.transactionHash` is set, the user operation was sent:** track it instead of resending.

| Response | What happened | What to do |
| :--- | :--- | :--- |
| `-32602`, no `data` | Rejected, nothing was sent: invalid fields, gas limits too low, or a simulation failure such as `AA25 invalid account nonce` | Fix and resend |
| `-32602` "submitted but is not yet included", with `data` | Sent but not included in time. The bundler still tracks it and bumps its gas if it gets stuck | **Don't resend.** Poll [`eth_getUserOperationReceipt`](/references/bundler/endpoints/eth_getUserOperationReceipt) with `data.userOpHash` |
| `-32521` "reverted onchain", with `data` | The bundle landed but reverted, so it didn't execute the user operation. Another bundler may have included it first | Check [`eth_getUserOperationReceipt`](/references/bundler/endpoints/eth_getUserOperationReceipt), and resend only if there is no receipt |
| `-32603` | The bundler couldn't send the bundle | Resend |
| No response (network error, client timeout, 5xx) | Unknown: it may have been sent | Resend |

A signed user operation can execute at most once, because the EntryPoint checks its nonce. Resending never runs it twice: if the first send landed, the resend is rejected with `AA25`, and you can look up the receipt by `userOpHash`.

To avoid duplicate sends, set `retryCount: 0` on your viem transport. By default viem resends up to 3 times on timeouts and internal errors.

## Nonces

- **No queue:** the user operation is simulated against the current chain state, so its nonce must be the account's current nonce for that key.
- **One at a time per key:** a user operation with nonce N+1, sent while N is in flight, is rejected with `AA25`. The response comes after inclusion, so send them one after another.
- **Base, next nonce right after a receipt:** the receipt arrives before its block is sealed, so nonce N+1 sent right after N's receipt can be rejected with `AA25 invalid account nonce`. Nothing is sent, so resend it after 1–2s.
- **Parallel sends:** to send in parallel from one account, use [different nonce keys](/guides/how-to/parallel-transactions).
